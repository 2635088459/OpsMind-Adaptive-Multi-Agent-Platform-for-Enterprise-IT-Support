# Support Console — 并发与幂等

> **Document ID:** LLD-SC-009
> **Domain:** `10-support-console`
> **状态:** Draft

---

## 1. 核心场景：多坐席协作同一批工单

这是本 domain 与 09 号 domain 并发问题的本质区别——09 号是"同一个人多设备"，10 号是"多个真人真的在同时工作"。处理原则已在 BI-SC-005 定下：**从不静默覆盖，永远让冲突可见**。

## 2. 乐观锁版本冲突（triage/assign/status-transitions）

```text
坐席 A 拉取工单，version=3
坐席 B 同时拉取，也是 version=3
坐席 A 先提交 triage（If-Match: 3）→ 成功，后端 version → 4
坐席 B 提交 assign（If-Match: 3）→ 后端拒绝，409
  → 前端进入 VERSION_CONFLICT
  → 重新拉取最新工单状态（version=4，已经是 A 的分诊结果）
  → 展示给坐席 B："此工单已被 {A 的名字} 分诊，是否仍要继续指派？"
  → 坐席 B 决定：放弃 / 基于最新状态重新提交
```

不自动重试、不自动合并两个人的修改——这是需要真人判断的场景。

## 3. 审批决策的并发（两个有权限的人同时想批准/拒绝同一个请求）

后端 `06-policy-approval-governance` 已经用 idempotency + 状态机保证只有一次决策生效（该 domain 自己的不变量）。前端职责：第二个点击的坐席收到"已被处理"的响应后，直接展示"该请求已由 {谁} 于 {何时} {批准/拒绝}"，而不是报一个通用错误。

## 4. 队列轮询与本地筛选状态的交互

轮询刷新队列数据时，如果坐席正在输入筛选条件/排序（`EDITING`-类临时 UI 状态），刷新不能打断坐席正在做的操作——新数据到达后先在后台合并，筛选/排序视图层面无感知地基于新数据重新计算，不重置坐席已经设置的筛选条件。

## 5. 明确不做的并发控制（MVP non-goal）

- 不做"坐席正在查看这个工单"的实时状态提示（协同感知，比如"Jamie 正在查看此工单"）——这是真实协作工具常见但非核心的功能，留给后续 phase。
- 不做审批请求的"认领"机制（多个有权限的人抢着处理同一个请求时谁先看到谁处理）——MVP 阶段允许多人都能看到并操作同一个待审批请求，靠 §3 的后端幂等兜底，不在前端引入乐观占用锁。
