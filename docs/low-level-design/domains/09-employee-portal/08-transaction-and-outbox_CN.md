# Employee Portal — 事务与 Outbox

> **Document ID:** LLD-EP-008
> **Domain:** `09-employee-portal`
> **状态:** Draft

---

## 1. 本篇为什么依然存在

09/08 号 domain 不持有数据库事务，也没有 outbox 表——这两个概念本身就是后端持久化层的东西。保留这篇文档位置，是为了明确回答一个真实会被问到的问题："前端怎么保证一次发送不会因为网络抖动变成两次真实的后端副作用？"——答案不是"前端自己搞一套事务"，而是**完全依赖后端已有的幂等机制**，本篇把这个依赖关系说清楚。

## 2. 前端如何"借用"后端的原子性保证

每一个会产生真实副作用的操作（发消息、确认方案、创建工单兜底路径），前端的责任只有一件事：**生成一个稳定的 `Idempotency-Key`，并且在重试时复用同一个 key，绝不重新生成**。

```text
用户点击"发送" → 生成 idempotencyKey = uuid() → 存入该次发送的本地状态
  → 请求失败/超时 → 重试 → 复用同一个 idempotencyKey
  → 请求成功 → idempotencyKey 作废，下一条消息生成新的
```

真正的原子性（消息落库 + 触发 agent 编排 + outbox 事件）全部发生在 `03-agent-runtime-orchestration` 内部，前端不知道、也不需要知道那一侧的事务边界怎么划——这正是分层的意义。

## 3. 唯一需要前端自己保证"原子性"的地方：本地草稿写入

`BI-EP-006` 要求会话过期时不能丢草稿。这是前端唯一自己负责的"写入不能丢"场景，用 `localStorage.setItem` 同步写入（不是 IndexedDB 异步事务），保证在页面即将卸载/token 过期的窄窗口内也能可靠落地。这不是一个真正的"事务"，只是提醒实现时选对存储 API。
