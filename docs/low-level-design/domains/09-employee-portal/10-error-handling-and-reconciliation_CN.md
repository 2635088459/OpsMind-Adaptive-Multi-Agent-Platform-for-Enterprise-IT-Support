# Employee Portal — 错误处理与降级

> **Document ID:** LLD-EP-010
> **Domain:** `09-employee-portal`
> **状态:** Draft

---

## 1. 分级降级策略

员工门户的第一原则：**agent 不可用，不代表员工应该被卡住**。每一层能力失效都要有一个明确的、更简单但仍然可用的下一层。

```text
理想路径：对话式自助/自动升级
    │ 03 号 domain（对话轮次能力）不可用
    ▼
降级 1：直连 02-ticket-workflow 的 POST /api/v1/tickets 兜底创建工单
    │ 02 号 domain 也不可用（极端情况）
    ▼
降级 2：展示离线提示 + 保留草稿（BI-EP-006），引导员工换渠道联系 IT
```

## 2. 具体错误场景

### 2.1 发消息请求超时/5xx
- 前端不自动把 turn 状态判定为失败——先重试（有限次数，指数退避），仍失败则进入 `AGENT_UNAVAILABLE`（见 `03-state-machine`）
- `AGENT_UNAVAILABLE` 态下，UI 提供"直接创建工单"按钮，走 §1 的降级 1 路径，员工不需要知道背后是"对话服务挂了"这种实现细节，只看到"帮你转成工单，人工会跟进"

### 2.2 附件上传失败
- 单个附件失败不阻塞其他附件/文字消息的发送——发送按钮的可用性只取决于"没有正在上传中"的附件，失败的附件允许移除或重试，不强制全部成功

### 2.3 SSE 连接断开
- 自动重连，指数退避，最多重试 N 次后转为轮询降级（每 30s 拉一次 `GET /api/v1/tickets/{id}`），状态从 `RECONNECTING` 转 `STALE` 并提示"进展可能不是最新的"
- 重连成功后必须用 `Last-Event-ID` 续传，不能"重新从头播放"整个历史状态迁移动画

### 2.4 ProposedAction 执行失败（后端返回执行错误，而非网络错误）
- 不是网络问题，是执行本身失败（例如工具调用真的报错）——不自动重试同一个 actionId，agent 侧应返回新的建议或转人工；前端只负责如实展示 agent 的下一句话，不自己决定重试策略

### 2.5 会话/Token 过期，恰好发生在发送中途
- BI-EP-006 的直接体现：请求因 401 失败时，先把当前输入框内容写入 `draft:{conversationId}`，再触发重新登录提示，成功登录后自动恢复草稿并允许重新点击发送（不自动重发——重发是否安全取决于上一次请求到底有没有真正落到后端，前端无法确定，所以交还给用户确认）

## 3. 明确不做的事

- 不在前端做"人工客服兜底聊天"这类完全跳过工单系统的旁路（那会绕开整个平台的审计/追溯能力）。
- 不静默吞掉任何真实错误——每一个降级路径都必须让员工清楚知道"发生了什么、接下来会怎样"，不能只是转圈圈或空白页。
