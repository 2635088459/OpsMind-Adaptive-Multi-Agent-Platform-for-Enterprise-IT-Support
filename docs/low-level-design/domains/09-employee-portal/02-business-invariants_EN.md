# Employee Portal — Business Invariants

> **Document ID:** LLD-EP-002
> **Domain:** `09-employee-portal`
> **Status:** Draft

---

## Note

The frontend does not adjudicate business rules itself — every invariant listed here is ultimately enforced for real by some backend domain. What follows are the invariants the frontend **must respect and never bypass or fake**, plus the invariants unique to the frontend's own (pure UI-level) concerns. Both categories are labeled clearly, not mixed together.

## BI-EP-001 — An employee can only see their own conversations and tickets

**Owner: backend enforcement** (domain 01 authentication + domain 02's ticket-workflow resource-ownership checks). The frontend's responsibility: any request fetching data by conversationId/ticketId carries a real JWT; it never constructs a "fetch everything, filter client-side" call — filtering must happen server-side, and the frontend only ever renders what the server has already filtered.

## BI-EP-002 — An attachment must finish uploading successfully before it can appear in a sent message

**Owner: frontend adjudication + object-storage-layer validation.** For a message's `attachments[]`, every `uploadStatus` must be `"ready"` before the send button is enabled; the send button is disabled while any attachment is `"uploading"`/`"failed"`. This is a pure UI state-machine rule (see `03-state-machine`) — it does not depend on, nor can it substitute for, server-side re-validation.

## BI-EP-003 — The client never executes an action requiring confirmation on its own

**Owner: frontend adjudication + backend re-enforcement.** When `ProposedAction.requiresConfirmation === true`, the client must never trigger any request with a real side effect before the user clicks "Confirm"; the confirmation request must carry that `actionId`, and the server must still perform its own permission/risk checks — it must not relax its own guardrails just because the frontend "already asked the user." The frontend's confirmation step is UX, not a security boundary.

## BI-EP-004 — Once a ticket exists, the ticket is the sole source of truth; the conversation transcript is a convenience view only

**Owner: frontend adjudication.** Once `Conversation.ticketId` is backfilled, ticket status is always read from `TicketStatusView` (fetched/streamed for real from ticket-workflow-service) — never inferred from the text of chat messages (for example, the frontend must never render a ticket as RESOLVED just because the agent's text said "it's fixed now" — it must wait until ticket-workflow-service's own status genuinely changes).

## BI-EP-005 — The client never fabricates or infers ticket state locally

A direct corollary of BI-EP-004, called out separately because it is the rule most likely to be broken "for the sake of a smoother experience": when the network is slow, the correct behavior is a loading state, not an optimistic guess that paints the status ahead of reality.

## BI-EP-006 — Session expiry must interrupt gracefully; a user's typed-but-unsent text must never be silently lost

**Owner: frontend adjudication.** When a JWT expires/is revoked, an in-progress conversation must: (a) preserve any typed-but-unsent draft text to local storage; (b) prompt re-login; (c) restore the draft after a successful re-login, rather than clearing it. This is the part of the employee experience most easily broken by backend-enforced authentication "in passing," and must be designed explicitly.

## BI-EP-007 — A high-risk proposal's confirmation copy must state the specific action and its impact

**Owner: frontend adjudication, content sourced from the backend.** `ProposedAction.summary` must never be an empty phrase like "I will perform an operation" — it must include the specific action name and a perceivable impact ("this takes about 30 seconds, and you'll be briefly logged out"). This copy is itself generated by the backend (agent-runtime); the frontend's invariant is: **it must never truncate or omit this text when rendering**, even under tight UI space constraints.
