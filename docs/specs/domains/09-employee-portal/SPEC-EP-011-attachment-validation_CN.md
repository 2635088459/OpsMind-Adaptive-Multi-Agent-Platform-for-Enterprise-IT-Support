# SPEC-EP-011 — Attachment Validation（附件校验）

> Domain: `09-employee-portal` | Phase: 04 — 证据文件切片 | 状态：Spec Planning

## 1. Spec 身份
`SPEC-EP-011`，`03-state-machine` §3.2 中 `VALIDATING` 状态自身的行为。

## 2. 目标
在花费一次上传往返之前，客户端先拒绝明显不可用的文件（类型不对、超出大小限制）。

## 3. 设计依据
`03-state-machine` §3.2；`01-domain-model` §"Attachment"（允许的 MIME 类型/最大大小，来自共享附件能力自己的契约）。

## 4. Actor
正在选择文件的员工。

## 5. 范围
`VALIDATING → UPLOADING`/`FAILED` 的判定，完全基于客户端可见的文件元数据（文件名、MIME 类型、字节大小）。

## 6. 非目标
内容级校验（例如图片是否真的能解码、恶意软件扫描）——这属于共享能力自己的服务端关切，客户端从不重复实现。

## 7. 前置条件
刚选完文件（轮次状态为 `IDLE`）。

## 8. 输入
所选 `File` 对象的 `type` 和 `size`。

## 9. 详细行为
对照白名单检查 MIME 类型，对照上限检查大小——通过 → `UPLOADING`；不通过 → `FAILED`，带具体原因（类型不对 vs. 太大），从不给一个笼统错误。

## 10. 交互状态迁移
`03-state-machine` §3.2 的 `VALIDATING` 节点及其两条出边。

## 11. 业务不变量
BI-EP-002——校验不通过的附件绝不能到达 `READY`，也绝不能在没有员工可见反馈的情况下被悄悄丢弃。

## 12. 幂等策略
不适用——纯本地同步计算，无网络调用。

## 13. 消费/依赖的契约
网络层面没有；白名单/大小限制的值本身来自共享附件能力发布的契约（是一个配置值，不是 API 调用）。

## 14. 安全
本客户端检查明确只是建议性的（`11-security-and-authorization` §3）——从不被当作安全边界。

## 15. 可观测性
校验拒绝原因在客户端记录，用于 UX 质量追踪，不作为安全信号发送。

## 16. 错误场景
文件类型不对 → `FAILED`，提示"不支持的文件类型"；文件过大 → `FAILED`，提示"文件太大"；两者遵循 BI-EP-002 用不同措辞区分。

## 17. 验收场景
一个 `.exe` 文件被以"不支持的类型"拒绝；一个 500MB 的图片被以"文件太大"拒绝；一个符合限制的有效 `.png` 顺利进入 `UPLOADING`。

## 18. 先写测试
针对校验函数的单元测试，覆盖两种拒绝原因和通过场景。

## 19. 完成定义
类型不对、太大、有效三种场景都被单元测试覆盖，且都有区分明确、员工可见的提示信息。
