# SPEC-EP-018 — Agent Unavailable Fallback（Agent 不可用兜底）

> Domain: `09-employee-portal` | Phase: 07 — 韧性与降级 | 状态：Spec Planning

## 1. Spec 身份
`SPEC-EP-018`，一个韧性阶段的 spec，没有自己专属的 use case——它是对 SPEC-EP-005/006 针对特定后端故障模式的强化。

## 2. 目标
当 `agent-runtime-service` 本身在消息发送时不可达或报错（不是正常的转人工，而是真正的后端中断）时，给员工一条如实、可操作的路径。

## 3. 设计依据
`10-error-handling-and-reconciliation` §2.1；`03-state-machine` §3.1（错误边）。

## 4. Actor
在后端中断期间发送消息的员工。

## 5. 范围
检测出一次不是正常应用层响应的发送失败（5xx、超时、网络错误），并渲染一条独立的"助手暂时不可用"通知，带一个手动建单兜底链接（指向已存在、真实的建单端点）。

## 6. 非目标
任何后端重试/熔断逻辑（那是 `agent-runtime-service` 自己的关切）；失败消息的自动重试（员工显式重试，遵循 BI-EP-007 式的状态如实原则）。

## 7. 前置条件
一次消息发送（SPEC-EP-005）以基础设施级错误而非正常响应失败。

## 8. 输入
失败发送的错误类型（超时/5xx/网络）。

## 9. 详细行为
遇到这类失败时，轮次状态迁移到一个独立的 `SEND_FAILED` 子状态（不是悄悄回到 `IDLE`），渲染失败的消息，带一个重试按钮和一个指向已有建单 UI/端点的"改为手动建单"链接。

## 10. 交互状态迁移
在 `03-state-machine` §3.1 的基础上扩展一条从 `SENDING` 出发、与正常 agent 响应明确区分的失败边。

## 11. 业务不变量
BI-EP-006（失败的草稿被保留，不丢失）以及 BI-EP-004（从不声称消息已被处理，如果实际没有）。

## 12. 幂等策略
重试复用同一条消息的 `Idempotency-Key`（遵循 SPEC-EP-005 §12），因此如果原始发送实际已在服务端落地，瞬时失败后的重试也不会导致重复处理。

## 13. 消费/依赖的契约
已存在、真实的手动建单端点（属于 domain 02）作为兜底路径。

## 14. 安全
无新增 scope——复用已有的建单 scope。

## 15. 可观测性
一个发送失败的客户端事件，可用于从前端自己的视角对后端中断进行告警。

## 16. 错误场景
本 spec 的全部范围按定义就是一个错误场景；对应的"如果这个兜底自己也失败了"的情况不在范围内（进一步回退到一个通用的错误边界）。

## 17. 验收场景
模拟一次发送时的 503，会渲染出 `SEND_FAILED` 状态，同时带一个重试按钮和一个能正常跳转的手动建单链接。

## 18. 先写测试
针对每种错误类型（超时/5xx/网络）模拟并断言正确兜底 UI 的组件测试。

## 19. 完成定义
三种失败类型都渲染出如实的兜底 UI；手动建单链接被验证能跳转到真实、已存在的端点。
