# SPEC-EP-021 — Scope Hardening（权限范围加固）

> Domain: `09-employee-portal` | Phase: 08 — 安全与发布加固 | 状态：Implemented

## 1. Spec 身份
`SPEC-EP-021`，对本 domain 目前为止所有 spec 的一次安全加固审计。

## 2. 目标
审计员工门户任何地方发起的每个 API 调用，确认每个都恰好携带其自身 spec 声明的 scope——不请求过宽的 token，也不存在仅因后端 bug 而"碰巧能用"的缺失 scope。

## 3. 设计依据
`11-security-and-authorization`（全部章节）；之前每个 spec 自己的 §14 安全章节。

## 4. Actor
不适用——这是一个工程/安全审计活动，不是面向终端用户的行为。

## 5. 范围
横切审查 SPEC-EP-001 到 SPEC-EP-020 每个网络调用实际附带的 token/scope，对照每个 spec 声明的 scope 逐一检查。

## 6. 非目标
任何新的后端 scope 定义（属于各自后端 domain 自己的 spec）。

## 7. 前置条件
SPEC-EP-001 到 SPEC-EP-020 已实现（或其 MSW mock 形式已就位以供审计）。

## 8. 输入
测试/开发构建中观察到的实际运行时请求头。

## 9. 详细行为
对每个端点调用点，断言 token scope 与声明的需求完全一致——同时标记权限不足（对真实后端会 403）和权限过宽（客户端请求了超出实际使用范围）两类问题。

## 10. 交互状态迁移
不适用。

## 11. 业务不变量
一条新的横切不变量：本应用中任何网络调用携带的 scope 都不能宽于其自身 spec 声明所需的范围。

## 12. 幂等策略
不适用。

## 13. 消费/依赖的契约
SPEC-EP-001 到 SPEC-EP-020 引用的所有契约，在此一并重新审查。

## 14. 安全
本 spec 的全部内容都是安全关切。

## 15. 可观测性
一份 scope 审计报告是本 spec 产出的成果物（纳入仓库或 CI 输出，不是运行时功能）。

## 16. 错误场景
任何发现使用了不正确 scope 的端点都是一个待修复项，作为本 spec 自身收尾的一部分被跟踪并修复，而非悄悄延后。

## 17. 验收场景
应用中每个调用点都通过 scope 审计且零发现项，或者所有发现项都在本 spec 关闭前修复。

## 18. 先写测试
针对每个发起网络调用的 hook，运行一次静态/lint 风格检查（如自动化不现实，则用人工审计清单）。

## 19. 完成定义
整个员工门户代码库中零未解决的 scope 问题。
