# SPEC-EP-016 — Confirm Resolution（确认已解决）

> Domain: `09-employee-portal` | Phase: 06 — 解决反馈闭环 | 状态：Implemented

## 1. Spec 身份
`SPEC-EP-016`，一个新的 use case，用于在问题看起来已解决后闭环。

## 2. 目标
让员工明确确认一个被提议/已执行的解决方案确实修好了他们的问题，把这个信号作为真实的工单解决确认反馈回去，而不只是一次 UI 关闭。

## 3. 设计依据
`01-domain-model` §"TicketStatusView"；`04-use-cases`（新增 use case，与本 spec 一同补充，因为原本 6 个里没单独列出）；ticket-workflow 自己的解决确认契约（已存在，属于 domain 02）。

## 4. Actor
工单已进入"待确认解决"状态的员工。

## 5. 范围
在一个已解决工单上展示"是的，修好了"/"没有，问题还在"的操作，调用真实的 ticket-workflow 确认端点。

## 6. 非目标
任何新的解决逻辑——本 spec 只调用一个 `02-ticket-workflow` 已有的确认契约，类比 support console 展示类似状态的方式。

## 7. 前置条件
工单状态（遵循 SPEC-EP-013 面板）为已解决/待确认状态。

## 8. 输入
员工的是/否回应。

## 9. 详细行为
"是的" → 调用 ticket-workflow 的确认端点（真实、已存在，属于 domain 02）→ 工单关闭；"没有" → 进入 SPEC-EP-017 的重开流程。

## 10. 交互状态迁移
这是一个 `TicketStatusView` 层面的关切（SPEC-EP-013 的面板），不是对话轮次状态机——可以独立于任何活跃对话轮次被触发。

## 11. 业务不变量
BI-EP-004——确认 UI 必须反映真实的后端解决状态，绝不能是本地假设的状态。

## 12. 幂等策略
每次确认/否认点击一个 `Idempotency-Key`，与 domain 02 自己针对该端点的幂等约定一致。

## 13. 消费/依赖的契约
ticket-workflow 已有的解决确认端点（真实，属于 domain 02——具体路径在接入前需对照 domain 02 自己的 API 契约文档确认）。

## 14. 安全
要求员工是该工单本人的提交者（后端强制执行）。

## 15. 可观测性
确认/否认调用带 `traceparent`。

## 16. 错误场景
确认调用失败——提供重试操作，工单状态保持最后已知值。

## 17. 验收场景
确认一个已解决工单，将其状态迁移为已关闭，并反映在 SPEC-EP-013 的面板里。

## 18. 先写测试
针对一个 mock 的确认端点，为"是"和"否"两条路径写组件测试。

## 19. 完成定义
两条路径针对 mock 都正确工作；domain 02 具体端点路径确认并接入后追加兼容性测试。
