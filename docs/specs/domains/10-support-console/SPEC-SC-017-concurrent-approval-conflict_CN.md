# SPEC-SC-017 — Concurrent Approval Conflict（并发审批冲突）

> Domain: `10-support-console` | Phase: 07 — 并发加固 | 状态：Spec Planning

## 1. Spec 身份
`SPEC-SC-017`，针对 `SPEC-PG-011` 建成的真实三方重放/冲突检查，强化 SPEC-SC-009 的批准/拒绝操作。

## 2. 目标
证明当两个坐席竞争决策同一个审批请求时，SPEC-SC-009 的批准/拒绝 UI 能正确展示"已被以不同方式决策"的结果——这正是 `SPEC-PG-011` 后端逻辑专门为防范而建的场景。

## 3. 设计依据
`SPEC-PG-011`（本 spec 验证对象的后端契约，根据项目记忆："严格的三方批准/拒绝重放检查"）；SPEC-SC-009。

## 4. Actor
两个正在查看同一张 `ApprovalCard`（SPEC-SC-008）并竞相决策的管理员/坐席。

## 5. 范围
一个专门的测试场景，证明 SPEC-SC-009 能正确处理 `SPEC-PG-011` 三方重放检查的全部 3 种结果：相同决策幂等重放（安全，相同 key）、相同决策不同 key（根据后端重放语义应仍然成功——需精确对照 `SPEC-PG-011` 自己的 spec 确认）、以及不同决策（被拒绝，如实展示）。

## 6. 非目标
任何新的后端重放逻辑（已真实存在，根据项目记忆对 `SPEC-PG-011` 的描述，是本 domain 消费的规格最严谨的契约）。

## 7. 前置条件
一个处于待决状态、正被两个操作者并发决策的审批请求。

## 8. 输入
两次近乎同时的批准/拒绝提交。

## 9. 详细行为
两次提交竞态；后端按 `SPEC-PG-011` 的真实三方检查决定结果；第二个操作者的 UI（遵循 SPEC-SC-009 §9）必须渲染实际的第一次决策，而不是一个通用失败。

## 10. 交互状态迁移
不适用——委托给 SPEC-SC-009 自己的状态处理。

## 11. 业务不变量
BI-SC-005，专门针对 `SPEC-PG-011` 自己真实的后端保证进行验证——本 spec 的任务是确认前端不会破坏一个已经存在的后端保护，而不是构建新的保护。

## 12. 幂等策略
从客户端直接验证 `SPEC-PG-011` 的 `commandIdempotencyKey` 语义。

## 13. 消费/依赖的契约
`SPEC-PG-011` 的批准/拒绝端点，特别是其文档化的三方检查行为。

## 14. 安全
除 SPEC-SC-009 自身要求外不适用。

## 15. 可观测性
一个冲突结果的客户端事件，可用于衡量真实的审批竞态频率。

## 16. 错误场景
本 spec 的全部内容就是 SPEC-SC-009 的错误/竞态场景。

## 17. 验收场景
两次竞态决策（一个批准，一个拒绝）解决后，第二个操作者会看到实际胜出的决策，遵循 `SPEC-PG-011` 自己定义的行为。

## 18. 先写测试
针对 `SPEC-PG-011` 文档化的响应契约模拟竞态的集成风格测试（接入前 mock，鉴于端点已真实存在，接入后实时验证）。

## 19. 完成定义
`SPEC-PG-011` 的全部 3 种结果都在 SPEC-SC-009 的 UI 中被正确反映；鉴于端点已存在，针对真实端点实时验证。
