# SPEC-SC-012 — Manual Status Transition（手动状态迁移）

> Domain: `10-support-console` | Phase: 05 — 人工工单操作 | 状态：Spec Planning

## 1. Spec 身份
`SPEC-SC-012`，实现 `UC-SC-06`。

## 2. 目标
使用 domain 02 已有的状态迁移端点，让坐席能手动把一个工单推进其真实的后端状态机（例如 `IN_PROGRESS → RESOLVED`）。

## 3. 设计依据
`04-use-cases` UC-SC-06；domain 02 真实的工单状态机及其迁移端点。

## 4. Actor
正在处理一个工单的支持坐席。

## 5. 范围
一个状态迁移控件（例如下拉框或按钮组），只展示从工单当前真实状态出发有效的迁移选项，以及对真实端点的调用。

## 6. 非目标
渲染/发明 domain 02 自己状态机中未定义的新迁移——本 spec 严格镜像后端允许的内容。

## 7. 前置条件
一个处于坐席可修改状态的工单。

## 8. 输入
所选的目标状态。

## 9. 详细行为
控件只渲染按工单当前状态有效的下一状态（从 domain 02 自己的状态机元数据拉取，或在测试中验证过的一份硬编码镜像）→ 提交 → 调用迁移端点 → 行/详情更新。

## 10. 交互状态迁移
直接触发 domain 02 自己真实的工单状态机——本 spec 不定义新的状态机。

## 11. 业务不变量
BI-SC-005——从一个陈旧的本地缓存状态尝试的迁移必须被后端如实拒绝（一个版本冲突场景），而不是在客户端悄悄成功，遵循 SPEC-SC-013。

## 12. 幂等策略
每次迁移提交一个 `Idempotency-Key`。

## 13. 消费/依赖的契约
domain 02 真实的工单状态迁移端点。

## 14. 安全
需要坐席自己的 `tickets:transition` scope。

## 15. 可观测性
调用带 `traceparent`。

## 16. 错误场景
无效迁移被拒绝（本地状态陈旧）——由 SPEC-SC-013 的版本冲突 UI 处理。

## 17. 验收场景
把一个工单从 `IN_PROGRESS` 迁移到 `RESOLVED` 成功并更新展示；尝试一次无效迁移（例如后端只允许 `RESOLVED → CLOSED` 时尝试 `RESOLVED → IN_PROGRESS`）被拒绝并如实展示。

## 18. 先写测试
针对真实契约的响应形状，为有效迁移和无效迁移拒绝写组件测试。

## 19. 完成定义
两种情况都针对 fixture 得到验证；一次实时集成检查确认对 domain 02 真实状态机的端到端行为。
