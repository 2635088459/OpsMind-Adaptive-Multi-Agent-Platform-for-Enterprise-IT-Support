# SPEC-SC-013 — Version Conflict Handling（版本冲突处理）

> Domain: `10-support-console` | Phase: 05 — 人工工单操作 | 状态：Spec Planning

## 1. Spec 身份
`SPEC-SC-013`，一个收尾 Phase 05 的横切强化 spec，覆盖 SPEC-SC-010/011/012 共同的并发风险。

## 2. 目标
为"3 个手动操作 spec 中任意一个的变更因本地版本陈旧被后端拒绝"这种情况，提供一套统一、一致的 UI 处理——这是 BI-SC-005 真实存在的多 agent 协作风险的直接后果（本 domain 不像 domain 09，存在多个人类以及 AI agent 本身可能同时触碰同一个工单）。

## 3. 设计依据
`01-domain-model` §BI-SC-005；`10-error-handling-and-reconciliation` §2。

## 4. Actor
分诊/指派/状态迁移尝试在与并发变更（来自另一个坐席或 `agent-runtime-service` 本身）的竞态中落败的任何坐席/管理员。

## 5. 范围
一个被 SPEC-SC-010、011、012 共享的冲突处理工具：遇到版本冲突（409 风格）响应时，丢弃本地乐观假设，重新拉取真实当前状态，并在让坐席重试前，准确展示底层发生了什么变化。

## 6. 非目标
任何后端乐观并发控制实现（已真实存在，遵循 domain 02/06 自己的版本机制）——本 spec 只是如实消费冲突信号。

## 7. 前置条件
一次来自 SPEC-SC-010/011/012 的变更因版本不匹配被拒绝。

## 8. 输入
冲突响应，包括（如果后端提供的话）导致拒绝的真实当前状态。

## 9. 详细行为
遇到冲突时：展示"该工单自你加载后已发生变化"的提示，把真实当前值与坐席尝试的变更并排展示，并提供丢弃或针对最新状态重新应用的选项。

## 10. 交互状态迁移
不适用——一个共享的错误恢复 UI 模式，不是一个新的状态机。

## 11. 业务不变量
BI-SC-005 本身——本 spec 是它在 UI 层的主要强制点。

## 12. 幂等策略
冲突后的每次重试都针对现在的当前状态使用一个全新的幂等 key，绝不盲目重放原始基于陈旧状态的请求。

## 13. 消费/依赖的契约
与 SPEC-SC-010/011/012 相同的 3 个端点，特别是它们的冲突响应形状。

## 14. 安全
不适用。

## 15. 可观测性
一个版本冲突的客户端事件，可用于理解生产环境中真实的碰撞率（为日后是否需要针对 domain 10 多 agent 协作假设做进一步 UI 投入提供依据）。

## 16. 错误场景
本 spec 的全部内容就是它所强化的 3 个变更 spec 的错误场景。

## 17. 验收场景
在一次分诊提交前模拟一次并发变更，会展示带真实当前值的冲突提示，而不是一个通用错误。

## 18. 先写测试
针对模拟冲突响应，为 3 种变更类型各写一个组件测试。

## 19. 完成定义
3 个变更 spec 都正确委托给这个共享的冲突处理行为；收尾 Phase 05。
