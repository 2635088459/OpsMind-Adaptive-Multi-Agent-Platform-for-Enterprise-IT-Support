# SPEC-SC-018 — Scope Hardening（权限范围加固）

> Domain: `10-support-console` | Phase: 08 — 安全与发布加固 | 状态：Spec Planning

## 1. Spec 身份
`SPEC-SC-018`，`SPEC-EP-021` 在 domain 10 的对应版本，因 SPEC-SC-006 真实存在的 3-domain 聚合面而在这里更为关键。

## 2. 目标
审计支持控制台任何地方发起的每个 API 调用——跨越它触及的全部 4 个后端 domain（02、05、06、08，及待定的 07）——确认每个都恰好携带其声明的 scope，特别关注 SPEC-SC-006 那个"3 个 scope 并集"的聚合调用。

## 3. 设计依据
`11-security-and-authorization`（全部章节）；之前每个 spec 自己的 §14 安全章节，特别是 SPEC-SC-006 的 §14。

## 4. Actor
不适用——一个工程/安全审计活动。

## 5. 范围
横切审查 SPEC-SC-001 到 SPEC-SC-017 每个网络调用的 token/scope。

## 6. 非目标
任何新的后端 scope 定义，特别是不尝试给已知的 `ApprovalController` 细粒度授权缺口（SPEC-SC-002 §6）打补丁——那个缺口在这里被记录，而不是悄悄绕过。

## 7. 前置条件
SPEC-SC-001 到 SPEC-SC-017 已实现。

## 8. 输入
测试/开发构建中观察到的实际运行时请求头。

## 9. 详细行为
对每个端点调用点（跨越触及的全部 4-5 个后端 domain），断言 token scope 与声明的需求完全一致；特别验证 SPEC-SC-006 的 3 个并发调用各自携带正确 scope 的 token，而不是用一个过宽的 token 覆盖全部 3 个。

## 10. 交互状态迁移
不适用。

## 11. 业务不变量
本应用中任何网络调用携带的 scope 都不能宽于其自身 spec 声明所需的范围——与 `SPEC-EP-021` 相同的不变量，在这里应用于更广的跨 domain 面。

## 12. 幂等策略
不适用。

## 13. 消费/依赖的契约
SPEC-SC-001 到 SPEC-SC-017 引用的所有契约，一并重新审查。

## 14. 安全
本 spec 的全部内容都是安全关切；风险最高的发现类别是 SPEC-SC-006 跨 3-domain 聚合中任何意外的 scope 泄漏。

## 15. 可观测性
一份 scope 审计报告是本 spec 产出的成果物。

## 16. 错误场景
任何发现使用了不正确 scope 的端点都是一个待修复项，在本 spec 关闭前修复。

## 17. 验收场景
应用中每个调用点都通过 scope 审计且零发现项。

## 18. 先写测试
针对每个发起网络调用的 hook，运行一次静态/lint 风格检查（或人工审计清单）。

## 19. 完成定义
整个支持控制台代码库中零未解决的 scope 问题，已知的 `ApprovalController` 缺口被明确重新确认为已记录状态（不是被悄悄打补丁）。
