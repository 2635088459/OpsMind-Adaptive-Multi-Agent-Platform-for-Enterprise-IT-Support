# SPEC-SC-018 / SPEC-SC-020 — Scope Hardening & Trace Propagation Coverage: Audit Report

> Both specs' own §15/§9 name this report (not a runtime feature) as the artifact they produce — the domain-10 analogues of `SPEC-EP-021`/`SPEC-EP-023` (see `docs/specs/domains/09-employee-portal/SPEC-EP-021-023-scope-and-trace-audit.md`), made more consequential here by a genuine 4-backend-domain surface (02 ticket-workflow, 06 policy-approval-governance, 07 evaluation-improvement, 08 observability-platform-via-BFF) and SPEC-SC-006's real 3-source aggregation. Written after every prior domain 10 spec (SPEC-SC-001–017/019) was implemented for real, auditing the actual running call sites and their real backend enforcement — not this domain's own spec prose.

## Methodology
Every real network call site in `apps/support-console/src/` was enumerated (`grep -rn "authedFetch(\|fetch(" src/`, excluding tests), then each was traced to its real backend endpoint's own scope/auth requirement — read directly from that endpoint's own `REQUIRED_SCOPE` constant, `@PreAuthorize` annotation, or security dependency in its own source, not assumed from this domain's own spec prose. The real Keycloak client's own granted scopes were read directly from `infrastructure/keycloak/opsmind-realm.json`, and the actual JWT issued to a real `support.agent` login was decoded live to confirm what the token really carries versus what each endpoint really checks.

## SPEC-SC-018 conclusion

**Two real findings, one fixed as a genuine scope-hardening action, one re-confirmed as an already-documented, out-of-scope gap.**

1. **Fixed**: the support-console Keycloak client (`infrastructure/keycloak/opsmind-realm.json`) and `user-access-authentication-service`'s own OAuth2 client registration (`application-local.yml`) both granted/requested 3 scopes — `ticket:close` (gates `CloseTicketController`/`CloseTicketApplicationService`), `ticket:request-approval` (gates `RequestApprovalController`/`RequestApprovalApplicationService`, an agent/workflow-originated approval-request-creation endpoint with `workflowId`/`actionId`/`actionType`/`riskContext` fields that have no honest human-suppliable equivalent in a manual console action), and `ticket:assign-route` (gates `UpdateTicketAssignmentController`'s own heavier team-routing reassignment variant, deliberately NOT the one SPEC-SC-011 wired) — that **zero real call sites in this app ever use**. Removed from both places. Live-verified end-to-end against a real running stack (fresh Keycloak realm import + rebuilt identity service, a real Authorization Code + PKCE login as `support.agent`): the resulting real JWT's own `scope` claim now reads exactly `openid profile email ticket:assign governance:audit:read tickets:timeline:internal ticket:transition ticket:triage tickets:read:queue ticket:resolve` — the 3 removed scopes are gone. Every real write flow this app actually uses (triage/assign/transition/resolve) still succeeds (a real 404 against a nonexistent ticket ID, proving the scope check passes and the call reaches the ticket lookup); a direct call to the now-unreachable `POST .../closure` with a valid body correctly comes back a real 403.
2. **Re-confirmed, not patched**: `ApprovalController` (grant/deny/GET) has zero `@PreAuthorize` at all — any authenticated caller, regardless of scope, can currently decide any approval request. This is the same gap SPEC-SC-002 §6 and SPEC-SC-008/009 already named; per this spec's own explicit non-goal ("not attempting to patch over the known `ApprovalController` fine-grained-authorization gap... documented, not silently worked around here"), it is recorded again here and left alone — fixing it would be a domain 06 backend-authorization decision, not a domain 10 scope-hardening one.

**A third finding, originally recorded here as an out-of-scope gap and later fixed in a deliberate follow-up** (with the user's own explicit sign-off, since it's a real cross-domain security-boundary decision — see the call-site inventory's own `fetchToolRequestEntries` row above for the full account): tool-integration-gateway's entire `/internal/tool-gateway/v1` router had zero caller-identity check of any kind, reaching well beyond the read this app calls into its own submit/decide/cancel write operations. Fixed with a real `X-Caller-Id`/`X-Caller-Type: SERVICE` gate on every write endpoint and real, GET-only CORS — both live-verified against a running instance.

A structural clarification worth recording: SPEC-SC-006/018's own text imagines auditing "3 separately-scoped tokens" for the aggregation call — that mechanism doesn't exist anywhere in this app (or in its BFF). Exactly one BFF-relayed token, sourced once at login, is reused unchanged for every call this app ever makes (identical to domain 09's own architecture) — so the real, correct audit unit is "does that one token's own granted scope set match what its call sites actually consume," which is what this audit did.

**Zero unresolved over/under-scope findings remain** after the fix above.

## SPEC-SC-020 conclusion

**One real bug found and fixed.** `useAiLog`'s 3 concurrent SPEC-SC-006 calls (timeline/governance-audit/tool-request) each went through `authedFetch`, which unconditionally generated a **fresh, unrelated** `traceparent` for every call (`headers: {..., traceparent: newTraceparent()}` always overwrote anything a caller supplied) — meaning the 3 sibling fetches that make up one logical "load this ticket's AI log" operation produced 3 completely disconnected traces, not one followable operation, directly contradicting this very spec's own §9 requirement.

Fixed in 3 places:
1. `src/lib/httpClient.ts` — `authedFetch` now only generates a fresh `traceparent` when the caller didn't already supply one (`init.headers?.traceparent ?? newTraceparent()`), a minimal, backward-compatible change — every other call site in this app that doesn't pass its own `traceparent` is completely unaffected.
2. `src/lib/trace.ts` — a new `newTraceContext()`/`TraceContext.traceparent()` pair: one shared `(trace-id, parent-span-id)` pair whose `traceparent()` method can be called repeatedly (once per fan-out call) while always returning a header sharing that same trace-id and parent-span-id.
3. `src/features/ailog/useAiLog.ts` — creates one `TraceContext` per `ticketId` (stable across re-renders and even a later scoped per-source retry) and passes its `traceparent()` value explicitly into all 3 of `fetchTimelineEntries`/`fetchGovernanceAuditEntries`/`fetchToolRequestEntries`.

Verified with a new test (`AiLogPanel.test.tsx`) capturing the real `traceparent` header MSW saw on 2 of the 3 concurrent requests and asserting they share the same 32-hex-character trace-id — confirmed passing.

Every other real call site in this app already carried its own, independent `traceparent` before this audit (each is a genuinely separate logical operation, not a fan-out that should share a parent): `fetchBrowserSessionToken`, `fetchTraceWaterfall`, every `evaluation/api.ts` read, and every other `authedFetch`-based call (queue, approval, triage, assignment, statusTransition) — confirmed by reading each one directly.

**Zero untraced call sites, and zero disconnected-fan-out call sites, remain** across `src/`.
