# SPEC-SC-019 — Partial Authorization Visibility（部分授权可见性）

> Domain: `10-support-console` | Phase: 08 — 安全与发布加固 | 状态：Spec Planning

## 1. Spec 身份
`SPEC-SC-019`，本 domain 聚合架构特有的一个安全加固 spec，把 SPEC-SC-007 的如实降级原则专门延伸到授权维度。

## 2. 目标
确认当一个支持坐席对 SPEC-SC-006 聚合的 3 个来源之一缺少 scope 时（例如一个坐席有 `tickets:read` 但没有 `governance-audit:read`），AI 日志面板对该来源展示一条如实的"你没有权限查看这份数据"提示——与 SPEC-SC-007 的"该来源不可用"（一次中断）明确区分——绝不悄悄省略该部分，仿佛那个来源本来就没有数据一样。

## 3. 设计依据
`11-security-and-authorization` §3；SPEC-SC-006；SPEC-SC-007（本 spec 与之区分的中断场景）。

## 4. Actor
scope 比完整管理员更窄、正在查看 AI 日志面板的支持坐席。

## 5. 范围
在 SPEC-SC-006 的 `Promise.allSettled` 处理中，把 403 风格的授权拒绝与任何其他失败区分开来，渲染一条独立的"访问受限"提示，而不是复用 SPEC-SC-007 的"暂时不可用"文案（那会错误地暗示重试可能有帮助）。

## 6. 非目标
任何新的后端授权逻辑——本 spec 只确保前端正确解读并如实标记一个已有的 403 响应，绝不与 5xx/超时混为一谈。

## 7. 前置条件
一个坐席的会话对 SPEC-SC-006 的 3 个来源中至少一个缺少 scope。

## 8. 输入
来自 3 个聚合拉取之一的 403 风格响应。

## 9. 详细行为
遇到 403（通过状态码与其他错误类型区分）时，渲染"你没有权限查看这份数据"，且不带重试按钮（重试无济于事，不同于 SPEC-SC-007 的中断场景）。

## 10. 交互状态迁移
不适用。

## 11. 业务不变量
延伸 BI-SC-003：一个权限缺口在查看的坐席看来绝不能像数据缺口或中断——这个区分很重要，因为正确的下一步操作不同（申请权限 vs. 等待重试）。

## 12. 幂等策略
不适用。

## 13. 消费/依赖的契约
与 SPEC-SC-006 相同的 3 个端点，特别是它们的 403 响应形状。

## 14. 安全
本 spec 的全部内容都是一个安全透明度关切。

## 15. 可观测性
一个权限拒绝的客户端事件，与 SPEC-SC-007 的失败事件区分，可用于理解真实世界中的角色配置缺口。

## 16. 错误场景
3 个来源同时 403——3 条独立的"访问受限"提示，不是一条通用提示。

## 17. 验收场景
一个缺少 `governance-audit:read` 的坐席，会针对那一个来源看到如实的访问受限提示，而另外两个正常渲染。

## 18. 先写测试
针对 3 个来源中恰好一个模拟 403 的组件测试，断言正确的独立文案且不出现重试按钮。

## 19. 完成定义
403 响应在全部 3 个来源中都能与中断正确区分，各自有独立、如实的 UI 文案；与 SPEC-SC-020 一起收尾 domain 10 的 Feature Spec roadmap。
