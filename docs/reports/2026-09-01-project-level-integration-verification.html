01

Why this happened

Every domain in the platform — ticket workflow, policy approval, memory & knowledge, tool integration, agent runtime, evaluation, user access, observability — had already been individually spec-complete and independently test-covered. None of the seven backend services had ever been started in the same place at the same time. Spec-complete and integration-verified turned out to be two different claims.

A shared Postgres, a shared RabbitMQ, a new multi-service Compose stack, and — because every Java service's endpoints require a genuinely signed JWT — a real Keycloak realm went up for the first time. What follows is what broke, and what it took to make it real.

02

Eight bugs, none of them visible in isolation

Every one of these was invisible to every existing test suite, because every existing test suite gives each service its own throwaway database and a random port. Only running the real services side by side surfaced them.

Flyway history table collision across services Fixed
ticket-workflow · policy-approval-governance · user-access-authentication

All three Java services wrote flyway_schema_history to the same default public schema. The moment two ran against the shared database at once, identical migration version numbers from different services read back as checksum mismatches. Scoped each service's history table into its own schema, and made each V001 migration's schema creation idempotent.

Docker healthcheck ports hardcoded to the wrong value Fixed
policy-approval-governance (8086) · user-access-authentication (8087)

Both Dockerfiles were copied from a sibling that really does run on 8080. Neither service's own healthcheck had ever actually been exercised before — Testcontainers-based tests bind to a random port and never touch this file.

Keycloak's issued tokens disagreed with themselves on port Fixed
keycloak

Setting KC_HOSTNAME to a bare hostname only pins the host half of every iss claim — the port still tracked whichever port the caller happened to connect through, 8081 from the host or 8080 from inside the network. Two callers, two different issuers. Fixed by pinning a full base URL.

A hardcoded scope claim gets silently overwritten Fixed
keycloak

scope is not an ordinary claim — Keycloak regenerates it from the client's actually-granted scopes after every mapper runs. A hardcoded-claim mapper aimed at it quietly loses. Fixed with a real, granted client scope instead.

No outbox dispatcher existed at all Major findingFixed
ticket-workflow

The write side of the outbox pattern was solid — every domain event landed transactionally in outbox_events. Nothing ever drained a row back out. published_at was NULL on every row, forever. Built a real claim‑publish‑retry dispatcher, exposed behind an admin/scheduler endpoint, mirroring the one working precedent already in the codebase.

Two domains built the same event twice, differently Major findingFixed
ticket-workflow ↔ policy-approval-governance

ticket-workflow's own ticket.approval-wait-started.v1 and governance's consumed ticket.approval.required.v1 were both legitimate, independently specified contracts for the same real-world fact — different name, different payload shape — that had simply never been reconciled. Neither was rewritten; a translation bridge stages a second, correctly-shaped event alongside the first.

A realm import silently drops Keycloak's own default scopes Fixed
keycloak

Declaring a realm's own clientScopes array replaces Keycloak's built-in defaults rather than adding to them — profile and email simply didn't exist, breaking the browser login the instant it asked for them. Added them back explicitly.

A description string overflowed a database column Fixed
keycloak

One of the fix comments above ran past Keycloak's own 255-character limit on a scope description and crashed the entire realm import at boot. Caught immediately in the logs; shortened.

04

Where the line was drawn

Not every open thread is a gap. Three things were looked at and deliberately left alone.

evaluation-improvement's call into agent-runtime is a documented stub — the agent-runtime side of that contract was never built, and its own docstring already says so. Confirmed, not discovered.
evaluation-improvement's call into policy-approval was checked field-for-field against governance's real request DTO. Every name and enum value matches. No live re-test was needed once the identical server-side endpoint had already been proven live from ticket-workflow's own call to it.
tool-integration-gateway's outbound calls target whatever endpoint a connector's own database row names — a dynamic, per-connector surface, not a fixed sibling link, and out of scope for a wiring check.
